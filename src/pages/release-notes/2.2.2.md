## Release Notes

Apache Ozone 2.2.2 is a maintenance release on top of Ozone 2.2.1 with bug fixes and dependency updates.

## Upgrade from 2.2.1

Ozone 2.2.2 introduces no new OM or HDDS layout features and does not change
the layout version relative to 2.2.1. No layout finalization is required solely
for this patch upgrade. If your cluster already has
an unfinished upgrade from an earlier release, assess that upgrade separately.
Follow the non-rolling procedure in the
[upgrade and downgrade guide](https://ozone.apache.org/docs/administrator-guide/operations/upgrade-and-downgrade/),
with the release-specific checks below.

### Before stopping the cluster

1. Verify cluster health. Back up the current configuration, service keytab
   files, certificates, and metadata. Preserve the existing
   OM, SCM, Datanode, and Recon storage directories during the upgrade. Retain
   the 2.2.1 binaries for recovery.
2. On secure clusters, review the following principal properties in the
   configuration distributed to **every SCM**, including SCM instances that
   issue or renew certificates. Values must match the service principals used
   by the corresponding daemons. Copying these principal settings does not
   require copying the other daemons' private keys or keytab files to SCM.

   | Property on SCM | Used for |
   | --- | --- |
   | `ozone.om.kerberos.principal` | OM certificate requests and block allocation/deletion |
   | `hdds.datanode.kerberos.principal` | Datanode certificate requests |
   | `ozone.recon.kerberos.principal` | Recon certificate requests |
   | `hdds.scm.kerberos.principal` | SCM certificate requests |

   SCM now checks the requesting service identity. Matching considers the
   service name, whether a host component is present, and the realm when one
   is configured; individual hostnames are not compared. Proxy identities
   do not qualify as service identities. A mismatch can prevent certificate
   issuance or renewal. Incorrect OM principal configuration can also prevent
   new block allocation or deletion when admin authorization is enabled.
   Correct the principal configuration rather than granting service accounts
   broad administrator access as a workaround.
3. If security and gRPC TLS are enabled, review the Recon known issue and
   conditional workaround below **before restarting with 2.2.2**. Preserve a
   usable Recon database. If you require a full SCM checkpoint download, defer
   the upgrade until a release or vendor-supported build fixes this issue.

### Known issue: Recon SCM checkpoint download with gRPC TLS

[HDDS-17235](https://issues.apache.org/jira/browse/HDDS-17235) requires SCM peer
certificates on SCM Ratis and inter-SCM gRPC connections. Recon downloads a
full SCM database checkpoint through the same inter-SCM gRPC service, but
presents a Recon leaf certificate. With both `ozone.security.enabled=true`
and `hdds.grpc.tls.enabled=true`, SCM 2.2.2 rejects that certificate.

This affects full SCM checkpoint downloads from both Recon 2.2.1 and Recon
2.2.2 to SCM 2.2.2. Logs may contain `Not an SCM certificate` or
`Rocks DB checkpoint downloading failed`; Recon may report
`GET_SCM_DB_SNAPSHOT_FAILED`.

Disabling `ozone.recon.scm.snapshot.enabled` is **not required for every
2.2.2 deployment**. This issue applies only when security and gRPC TLS are
both enabled. With this setting enabled, Recon attempts a full checkpoint
download at startup only when the difference between its container count and
SCM's exceeds the configured threshold. An affected download fails; a restart
that does not need a full checkpoint does not encounter this failure.

For an existing Recon instance with a usable database, you can avoid that
startup download by setting the following in **Recon's** `ozone-site.xml`
before restarting Recon:

```xml
<property>
  <name>ozone.recon.scm.snapshot.enabled</name>
  <value>false</value>
</property>
```

This is a limited workaround: it skips startup SCM snapshot initialization,
while periodic container reconciliation continues to run. It does not repair
full checkpoint downloads or prevent manual full snapshot requests from being
attempted. Preserve Recon's database and avoid requesting a full SCM snapshot
refresh. The workaround does not provide a way to initialize a new Recon
instance or rebuild a missing or unusable database through a full checkpoint.

Ozone 2.2.2 has no configuration workaround that restores full SCM checkpoint
downloads while keeping gRPC TLS enabled. If you require this capability,
defer the upgrade until a release or vendor-supported build fixes the issue.
Once a fix is available, follow its upgrade instructions before restoring
`ozone.recon.scm.snapshot.enabled=true` and verifying a full checkpoint download.

This issue and the workaround are based on a review of the released source;
they have not been validated in a live secure-cluster upgrade test.

## Changelog

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

### Fixed

- Treat renaming an FSO file to itself as a no-op. ([HDDS-16779](https://issues.apache.org/jira/browse/HDDS-16779))
- Preserve the container state update path used during upgrades. ([HDDS-16169](https://issues.apache.org/jira/browse/HDDS-16169))
- Avoid updating the container delete transaction ID when appending to the SCM delete log. ([HDDS-15634](https://issues.apache.org/jira/browse/HDDS-15634))
- Allow repair tools to load RocksDB OPTIONS files written by newer RocksDB versions. ([HDDS-17144](https://issues.apache.org/jira/browse/HDDS-17144))
- Complete certificate inspection futures when a request passes inspection. ([HDDS-17030](https://issues.apache.org/jira/browse/HDDS-17030))
- Improve validation of multipart upload IDs and part numbers in OM requests. ([HDDS-17161](https://issues.apache.org/jira/browse/HDDS-17161), [HDDS-17162](https://issues.apache.org/jira/browse/HDDS-17162))
- Return `INVALID_REQUEST` for invalid replication configurations in bucket property and key creation requests. ([HDDS-17299](https://issues.apache.org/jira/browse/HDDS-17299))
- Validate the key prefix and container ID when importing a container. ([HDDS-17182](https://issues.apache.org/jira/browse/HDDS-17182))

### Changed

- Upgrade Jackson to 2.21.7. ([HDDS-16644](https://issues.apache.org/jira/browse/HDDS-16644))
- Upgrade Netty to 4.1.139. ([HDDS-17085](https://issues.apache.org/jira/browse/HDDS-17085))
- Upgrade the Develocity Maven extension to 2.6.0. ([HDDS-16713](https://issues.apache.org/jira/browse/HDDS-16713))
