A storage upgrade usually starts with a familiar question: what changes for my data? For Apache Ozone 2.3.0, put another question near the top of your checklist: which Java runtime will run my services?

The upcoming release raises the minimum Java version for server components to **Java 17**, adds **JDK 25 runtime support**, and moves the internal **Jetty version from 9.4 to 12**. The release drops server support for Java 8 and Java 11. Servers support **JDK 17, 21, and 25**, while clients support **JDK 8, 11, 17, 21, and 25**.

## One release, two Java decisions

Java 17 sets the minimum for building and running Ozone servers. The supported server runtimes are JDK 17, 21, and 25. Clients retain a wider range: JDK 8, 11, 17, 21, and 25.

Here is what to plan for in Ozone 2.3.0:

| Area | Ozone 2.3.0 support |
| --- | --- |
| Server components and admin tools | Supported runtimes: JDK 17, 21, and 25; Java 17 minimum for building |
| Removed server runtime support | Java 8 and Java 11 |
| Client components | Supported runtimes: JDK 8, 11, 17, 21, and 25; Java 8 remains supported for building |
| Internal Jetty dependency | Upgrade from 9.4 to 12 |

The server baseline change is tracked in [HDDS-14439](https://issues.apache.org/jira/browse/HDDS-14439). Java 25 runtime support is tracked in [HDDS-15672](https://issues.apache.org/jira/browse/HDDS-15672).

## The server moves forward; clients keep their flexibility

For operators, the Java 17 requirement belongs in the upgrade plan for SCM, OM, Datanodes, Recon, and the S3 Gateway. Remember the machines that run admin tools, too: the new baseline includes those tools, even when they run on separate administration hosts.

That distinction matters in a shared environment. A cluster administrator can move the Ozone services to a newer Java baseline without requiring every application team to migrate its Java runtime at the same time. Applications using Ozone clients can continue running on Java 8 or Java 11, or use JDK 17, 21, or 25.

Java 8 and Java 11 are no longer supported on the server side. If your servers or administration hosts still use either version, move them to JDK 17, 21, or 25 before deploying Ozone 2.3.0.

## Why Jetty is part of the story

Java baselines influence more than the language features available to developers. They also determine which versions of important libraries a project can adopt.

Ozone's move from Jetty 9.4 to Jetty 12 is a concrete example. Jetty is the embedded web server behind Ozone's HTTP services. Jetty 12 requires Java 17 or later, while Jetty 9.4 has reached the end of community support, as documented in the [Jetty compatibility table](https://jetty.org/docs/jetty/12/).

Raising Ozone's server baseline clears the way for that dependency upgrade, tracked in [HDDS-8280](https://issues.apache.org/jira/browse/HDDS-8280). This brings the embedded web server onto a supported Jetty release line.

### What to check during the upgrade

Ozone includes compatibility fixes for the Jetty 12 migration, but administrators should check a few integrations:

- **S3 secret-management scripts:** Error codes now appear in the plain-text response body instead of a custom HTTP reason phrase. Update scripts that parse the HTTP status-line text.
- **URLs and proxies:** Jetty 12 validates request URIs more strictly. Ozone preserves handling for special characters in S3 keys and HttpFS paths; test representative requests through your normal clients and reverse proxies.
- **Monitoring and log access:** Verify `/jmx`, `/conf`, and HTTPS access with your usual authentication configuration. If the log directory is unavailable, the service can start without exposing `/logs`.

See [HDDS-8280](https://issues.apache.org/jira/browse/HDDS-8280) for the migration details.

## JDK 25: another runtime option

JDK 25 runtime support gives teams adopting newer JDKs a way to bring Ozone along, on both servers and clients. Servers can use JDK 17, 21, or 25, so teams already running JDK 17 or 21 can stay with their current Java version.

Before adopting a newer runtime, measure how it behaves with your workload. Test representative reads and writes, watch garbage collection and memory use, and compare request latency under your own workload. Use those results to guide your runtime choice.

See [HDDS-15672](https://issues.apache.org/jira/browse/HDDS-15672) for the JDK 25 work, and check the final 2.3.0 release notes before selecting your production runtime.

## Getting ready for 2.3.0

A little preparation now can prevent surprises during the upgrade:

1. **Inventory the Java runtime used by each service and admin tool.** Check service definitions, deployment images, and `JAVA_HOME`. The Java version in an interactive shell may differ from the one that starts a service.
2. **Replace Java 8 and Java 11 on servers.** Choose JDK 17, 21, or 25 for server components and admin tools. Ensure server build environments use Java 17 or later.
3. **Test the runtime you intend to deploy: JDK 17, 21, or 25 for servers.** Review JVM options and exercise startup, reads, writes, and administrative operations in a staging cluster.
4. **Check web access after the Jetty upgrade.** Exercise the S3 Gateway and service web interfaces with your usual security and proxy configuration.
5. **Keep client planning separate.** Clients support JDK 8, 11, 17, 21, and 25; the server change does not require applications on Java 8 or Java 11 to migrate their runtime.

Ozone 2.3.0 gives operators a clear Java baseline and room to adopt a newer runtime, while the Jetty upgrade updates the embedded web server. Start with the Java inventory: it is a small task now that can make release day much less eventful.
